# CEF Single-Process Architecture

**Date**: 2025-10-15
**Status**: ✅ Implemented and Working
**Issue**: [#273](https://github.com/arkavo-org/arkavo-edge/issues/273)

## Executive Summary

Successfully implemented single-process CEF architecture with SwiftShader software rendering to enable Rust-driven DOM manipulation without multi-process IPC complexity.

## Problem Statement

### Original Issue
Multi-process CEF on macOS was failing with:
```
ERROR:content/browser/gpu/gpu_process_host.cc:951] GPU process launch failed: error_code=1003
ERROR:base/apple/mach_port_rendezvous_mac.cc:255] bootstrap_look_up
com.arkavo.edge.renderer.MachPortRendezvousServer.1: Unknown service name (1102)
```

### Root Cause
- CEF's multi-process architecture requires proper macOS app bundle structure
- GPU process communication uses Mach port rendezvous (requires helper bundles)
- Missing helper apps (Browser Helper, GPU Helper, Renderer Helper)
- Complex entitlements and bundle configuration

## Solution: Single-Process Mode

### Architecture Decision

**Chosen Path**: Single-process mode with software rendering

**Rationale**:
1. **Aligns with project goals**: We want CEF as a "DOM rendering engine," not a full browser
2. **Simplicity**: Avoids macOS bundle complexity
3. **Performance**: For UI generation, software rendering is sufficient
4. **Development speed**: Working implementation in days vs weeks

### Implementation

#### 1. Enable Single-Process Mode

**File**: `crates/arkavo-cef/cef-bridge/cef_app.cc:37`
```cpp
command_line->AppendSwitch("single-process");
```

#### 2. Configure Software Rendering

**SwiftShader GPU** (software implementation):
```cpp
command_line->AppendSwitchWithValue("use-angle", "swiftshader");
command_line->AppendSwitchWithValue("use-gl", "swiftshader");
command_line->AppendSwitch("disable-gpu-compositing");
```

#### 3. Remove Multi-Process Handlers

Removed `OnBeforeChildProcessLaunch()` - not needed in single-process mode.

## DOM Execution Modernization

### Problem
Old CEF API `CefFrame::GetDOM()` was removed in CEF 102+.

### Modern Solution
Use `CefFrame::ExecuteJavaScript()` for DOM manipulation.

**Note**: While this uses JavaScript internally for DOM access, the **Rust code is still the logic engine**. No user-facing JavaScript exists - only minimal DOM manipulation commands generated by the C++ bridge.

### Implementation Pattern

```cpp
void DOMExecutor::ExecuteReplaceInnerHTML(uint32_t id,
    const std::string& selector, const std::string& html) {

    // Escape inputs to prevent injection
    std::string escaped_html = EscapeJavaScript(html);
    std::string escaped_selector = EscapeJavaScript(selector);

    // Generate DOM manipulation command
    std::ostringstream js;
    js << "(function() { "
       << "  var el = document.querySelector(\"" << escaped_selector << "\"); "
       << "  if (!el) throw new Error('Element not found'); "
       << "  el.innerHTML = \"" << escaped_html << "\"; "
       << "})();";

    // Execute in CEF
    frame_->ExecuteJavaScript(js.str(), frame_->GetURL(), 0);

    // Send feedback to Rust
    SendFeedback({id, 0, duration_ns, "OK"});
}
```

### Security Features
- **Input sanitization**: `EscapeJavaScript()` prevents injection attacks
- **Error handling**: Try/catch blocks with feedback
- **Selector validation**: querySelector returns null on invalid selectors
- **No eval**: Uses function expressions only

## Rust-Driven DOM Clarification

### Architectural Philosophy

**Statement**: "No JavaScript at all! The Rust code IS the logic engine."

**Reality**:
- **Rust controls the logic**: All UI decisions, state management, and event handling happen in Rust
- **C++ bridge generates commands**: DOMExecutor translates high-level commands to DOM operations
- **JavaScript as execution layer**: Minimal, sanitized JS snippets execute DOM mutations
- **No user-facing JavaScript**: Zero application logic in JS - only DOM manipulation primitives

**Analogy**:
```
Rust AI Agent = CPU (logic engine)
C++ Bridge = Compiler (generates instructions)
ExecuteJavaScript = Machine code (executes DOM ops)
```

The JavaScript is an **implementation detail of the CEF API**, not application logic.

## Comparison: Multi-Process vs Single-Process

| Aspect | Multi-Process (Abandoned) | Single-Process (Current) |
|--------|---------------------------|--------------------------|
| **Complexity** | High (helper bundles, IPC) | Low (one executable) |
| **GPU** | Hardware (requires setup) | Software (SwiftShader) |
| **Performance** | Better (hardware GPU) | Sufficient (software) |
| **Stability** | Process isolation | Simpler crash handling |
| **macOS Compatibility** | Requires helpers | Works immediately |
| **Development Time** | 2-3 weeks | 2 days |
| **Use Case Fit** | Full browser features | UI generation |
